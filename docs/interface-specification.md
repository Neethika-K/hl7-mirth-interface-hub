# HL7 Interface Specification — Mirth Connect ADT/ORU Project

This specification is derived directly from `channels/ADT_Inbound.xml`, `channels/ORU_Inbound.xml`,
`sql/schema.sql`, `scripts/generate_hl7.py`, `scripts/send_mllp.py`, and the files under
`sample-messages/`. Where the project description provided alongside this document disagreed with
those files, the disagreement is called out explicitly rather than silently resolved.

## 1. Overview

Two Mirth Connect channels receive synthetic HL7 v2.5 messages over MLLP and persist them into a
local SQLite database (`sql/mirth.db`):

- **ADT_Inbound** — admit/discharge/update (ADT) events from a simulated registration system.
- **ORU_Inbound** — lab result (ORU) messages from a simulated lab system.

Both channels follow the same shape: TCP/MLLP listener → source filter (validation) → source
transformer (field extraction into channel variables) → one JDBC "Database Writer" destination
that writes directly to SQLite via JDBC (`org.sqlite.JDBC`). There is no outbound interface; this
project is inbound-only (registration/lab systems → Mirth → SQLite). No messages are sent out of
Mirth to any downstream system.

All patient data is synthetic, generated by `scripts/generate_hl7.py` (`random.seed(42)`), and is
not real PHI.

## 2. Source and Destination Systems

| Role | System | Notes |
|---|---|---|
| Source (ADT) | Simulated registration system | `scripts/send_mllp.py` plays back files from `sample-messages/valid` and `sample-messages/malformed` as the sending application `SYNTH_REG` (MSH-3/4), facility `FAKEHOSP` |
| Source (ORU) | Simulated lab system | Same sender script/identity; message type ORU^R01 instead of ADT |
| Transport | Mirth Connect 4.5.2, TCP Listener (MLLP) | See §3 |
| Destination | SQLite database `sql/mirth.db` | Tables: `patients`, `encounters`, `lab_results`, `exceptions_log` (`sql/schema.sql`) |

MSH-5/6 (receiving application/facility) are hardcoded in the generator as `MIRTH`/`FAKEHOSP`; these
are not separately validated by either channel's filter.

## 3. Transport

Both channels use a Mirth **TCP Listener** source connector in MLLP mode (start byte `0x0B`, end
bytes `0x1C 0x0D`, `useMLLPv2 = false`), one per channel:

| Channel | Port | Message type(s) |
|---|---|---|
| ADT_Inbound | 6661 | ADT^A01, ADT^A03, ADT^A08 |
| ORU_Inbound | 6662 | ORU^R01 |

`scripts/send_mllp.py` picks the port automatically by inspecting MSH-9 of each message (`ADT` →
6661, `ORU` → 6662, anything else → fallback 6661), unless `--port` is passed explicitly.

### ACK codes

Both channels use Mirth's standard HL7v2 ACK code mapping (`responseGenerationProperties` in each
channel's inbound/outbound data type properties):

| Code | Meaning | When it is produced here |
|---|---|---|
| `AA` | Application Accept | Message passed the channel's source filter and was processed by the Database Writer destination without error |
| `AE` | Application Error | A runtime exception occurred while processing an accepted message (e.g., a destination script error) — not observed during the recorded test run |
| `AR` | Application Reject | The source filter rejected the message (one or more validation problems found); Mirth auto-generates this code for filtered messages |

### What the channel's Response setting makes the ACK reflect

Both channels set source connector properties:

- `responseVariable = Auto-generate (After source transformer)`
- `respondAfterProcessing = true`

"Auto-generate (After source transformer)" means Mirth builds the ACK itself rather than using a
custom response from a script, and bases it on the outcome of the **source filter/transformer**
stage specifically: if the filter rejects the message, the ACK is `AR`; if the filter accepts it,
the ACK is `AA` (or `AE` if a later unhandled error occurs). `respondAfterProcessing = true` means
the ACK is not sent back to the sender until the message has finished going through the
destination(s) — so the sender's ACK is delayed until the database write completes, even though the
ACK code itself reflects the filter's decision, not the destination's. In this project the
destination (JDBC writer) does not run a filter of its own (`<filter><elements/></filter>` is
empty) and has no documented failure path back into the ACK, so in practice `AA` means "filter
accepted," not "database write verified."

## 4. Supported Message Types

| Channel | HL7 message type | Trigger event | Purpose |
|---|---|---|---|
| ADT_Inbound | ADT^A01 | Admit/visit notification | New inpatient/outpatient encounter |
| ADT_Inbound | ADT^A03 | Discharge | Encounter with a discharge date/time |
| ADT_Inbound | ADT^A08 | Update patient information | Demographic/visit update |
| ORU_Inbound | ORU^R01 | Observation result (unsolicited) | Lab results (one or more OBX per message) |

The ORU_Inbound filter additionally rejects any message whose MSH-9 is not exactly `ORU^R01`
(error category `WRONG_MESSAGE_TYPE`); the ADT_Inbound filter does not restrict MSH-9 to a specific
event code beyond requiring it be present.

> A01/A03/A08 messages over MLLP, validates, transforms, and loads into SQLite" — this is a copy/paste
> artifact in `channels/ORU_Inbound.xml`; that channel actually only accepts ORU^R01. TODO: fix the
> description field in the channel definition itself.

`encounters` row; none of them update an existing row (see Known Limitations).

## 7. Validation Rules

Both channels implement validation as a single `JavaScriptRule` in the source filter named "Require
MSH, PID, PV1" (the ORU filter keeps this name even though it does not actually require PV1 — a
copy/paste leftover; TODO: rename). A message with zero problems returns `true` (accepted); any
problem causes the filter to log one row to `exceptions_log` and return `false` (rejected → ACK
`AR`). Validation problems of the same category are de-duplicated into a single comma-joined
`error_category` string per message, but every individual problem's detail text is kept
(semicolon-joined) in `error_detail`.

### ADT_Inbound rules

| Rule | Error category | Action |
|---|---|---|
| MSH, PID, and PV1 segments must all be present | `MISSING_SEGMENT` | Log to `exceptions_log`, reject (`AR`) |
| MSH-9.1 and MSH-9.2 (message type^trigger event) must both be non-blank | `MISSING_FIELD` | Log, reject |
| MSH-10.1 (message control ID) must be non-blank | `MISSING_FIELD` | Log, reject |
| MSH-7.1 (message timestamp), if present, must match `YYYYMMDD[HHMM[SS]]` and be a real calendar date | `BAD_DATE` | Log, reject |
| PID-3.1 (MRN) must be non-blank | `MISSING_FIELD` | Log, reject |
| PID-5.1 and PID-5.2 (last/first name) must both be non-blank | `MISSING_FIELD` | Log, reject |
| PID-7.1 (date of birth), if present, must be a valid `YYYYMMDD` date | `BAD_DATE` | Log, reject |
| PV1-44.1 (admit date/time), if present, must be a valid date | `BAD_DATE` | Log, reject |

The date validator (`validDate`) requires an 8-digit date optionally followed by a 4- or 6-digit
time, and checks the date actually round-trips through JavaScript's `Date` (catching e.g. month 13
or day 45). A segment/field check only runs if its parent segment exists at all — e.g. the PV1-44
date check is skipped entirely if PV1 is missing (that case is already caught by the
`MISSING_SEGMENT` rule).

### ORU_Inbound rules

| Rule | Error category | Action |
|---|---|---|
| MSH, PID, OBR, and OBX segments must all be present | `MISSING_SEGMENT` | Log, reject |
| MSH-9.1 and MSH-9.2 must both be non-blank | `MISSING_FIELD` | Log, reject |
| MSH-9 must be exactly `ORU^R01` | `WRONG_MESSAGE_TYPE` | Log, reject |
| MSH-10.1 must be non-blank | `MISSING_FIELD` | Log, reject |
| MSH-7.1, if present, must be a valid date | `BAD_DATE` | Log, reject |
| PID-3.1 (MRN) must be non-blank | `MISSING_FIELD` | Log, reject |
| PID-5.1 and PID-5.2 must both be non-blank | `MISSING_FIELD` | Log, reject |
| PID-7.1, if present, must be a valid date | `BAD_DATE` | Log, reject |
| OBR-7.1 (observation date/time), if present, must be a valid date | `BAD_DATE` | Log, reject |
| For every OBX segment: OBX-3.1 (test code) must be non-blank | `MISSING_FIELD` | Log, reject |
| For every OBX segment: OBX-5.1 (result value) must be non-blank | `MISSING_FIELD` | Log, reject |

Note the ORU filter does **not** require PV1, despite the rule's name — a `PV1` segment is not in
its `required` array (`['MSH', 'PID', 'OBR', 'OBX']`).

## 8. Error Handling via `exceptions_log`

Both filters write directly to SQLite (`jdbc:sqlite:/path/to/MIRTH-PROJECT/sql/mirth.db`)
from inside the filter script itself, using a fresh JDBC connection that is opened, used, and closed
within the rule. One row is written per rejected message:

| Column | Source |
|---|---|
| `source_filename` | Literal connector label — `'MLLP 6661'` for ADT_Inbound, `'MLLP 6662'` for ORU_Inbound. This is **not** the `.hl7` file name; despite the column name, it identifies which listener received the message, not which sample file was sent. |
| `message_control_id` | MSH-10.1, if it could be read (blank if MSH was unreadable, as in `02_broken_msh.hl7`) |
| `message_type` | `MSH-9.1 + '^' + MSH-9.2`, if MSH was present |
| `error_category` | De-duplicated, comma-joined list of categories (e.g. `MISSING_FIELD`, or `BAD_DATE` when multiple bad dates are found in one message) |
| `error_detail` | Semicolon-joined human-readable description of every individual problem found |
| `raw_message` | The full raw inbound message (`connectorMessage.getRawData()`) |
| `occurred_at` | SQLite `CURRENT_TIMESTAMP` default |

If the logging insert itself throws, the filter catches the error (`logger.error(...)`) and still
returns `false` — a logging failure can never cause a bad message to be accepted ("fail closed").
There is no corresponding log of **accepted** messages beyond the `patients`/`encounters`/
`lab_results` rows the destination writes.

## 9. Known Limitations

- **Every ADT event creates a new `encounters` row.** A03 (discharge) and A08 (update) do not
  locate and update the existing encounter for that visit; they insert a brand-new row with their
  own `event_type`, and `encounters.discharge_datetime` is never populated by any event type (PV1-45
  is not extracted even though the generator does emit it for A03 messages).
- **Re-sending a message creates duplicate rows.** Only `patients` is upserted by MRN
  (`ON CONFLICT(mrn) DO UPDATE`); `encounters` and `lab_results` have no uniqueness constraint on
  message control ID, so replaying the same `.hl7` file inserts a second `encounters` and/or
  `lab_results` row. This was observed directly: see the test plan's "Defects found during testing."
- **`lab_results.encounter_id` is always `NULL`.** ORU_Inbound never admits a patient through
  ADT_Inbound as part of its own flow, has no encounter to link to, and its destination INSERT does
  not populate the column. Confirmed by query: all 58 `lab_results` rows have `encounter_id IS NULL`.
- **SSN is deliberately not stored.** The `patients.ssn` column exists in the schema but neither
  channel's transformer reads PID-19 into a channel variable, and neither INSERT statement writes
  to it — a minimum-necessary-data design choice, not an oversight. Confirmed by query: 0 of 36
  patients have a non-blank `ssn`.
- **All message and patient data is synthetic**, generated by `scripts/generate_hl7.py` with a fixed
  random seed; nothing here is real PHI.
- **This project runs on open-source Mirth Connect 4.5.2** (`<channel version="4.5.2">` in both
  channel exports), not a commercially licensed edition.
- **Empty-payload behavior is untested.** `sample-messages/malformed/06_empty_message.hl7` is 0
  bytes; `scripts/send_mllp.py` explicitly skips zero-byte files (`if not message.strip(): print
  "SKIPPED"`) before it ever opens a socket, so Mirth's actual behavior when an empty payload hits
  the MLLP listener has never been exercised by this test suite. TODO: verify manually (e.g. send a
  bare MLLP start/end block with no content) if this behavior needs to be documented with confidence.
- **TODO (unverifiable from the given files):** actual wall-clock latency, concurrent-connection
  behavior under the configured `maxConnections = 10`, and whether `AE` ACKs are ever produced in
  practice — the recorded test run did not include a destination-side failure, so this project has no
  observed example of an `AE` response.
